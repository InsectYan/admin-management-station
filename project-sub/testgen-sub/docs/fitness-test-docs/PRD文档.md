# 会员邀请、授权与默认承接规则 PRD
## 1. 功能定位
本需求用于定义会员通过管理端邀请、品牌旗下教练邀请、自由教练邀请进入系统时，系统如何完成注册登录、授权、门店承接、教练服务关系建立、会员状态初始化及历史关系保留。
本需求的核心不是简单“创建会员”，而是：
> 通过邀请完成会员授权，并基于邀请来源建立对应的服务主体关系。
会员主档保持唯一；不同品牌、门店、教练对该会员形成的服务关系可以并存，不应互相覆盖。

## 3. 核心设计结论
1. 会员主档唯一，不因多次扫码、多个品牌、多个教练邀请而重复创建。
2. 管理端邀请时，会员授权的是品牌，默认进入邀请门店公海。
3. 品牌教练邀请时，会员授权的仍然是品牌，不是教练个人；但系统同时建立该会员与邀请教练的体验服务关系。
4. 自由教练邀请时，会员授权的是教练本人，不经过品牌、门店、公海池；MVP 阶段不开放该能力，但底层关系模型需要预留。
5. 一个会员可以授权多个品牌，也可以与多个品牌下的多个教练建立服务关系。
6. 新邀请不得覆盖会员已有的品牌授权、门店承接、在服关系或历史服务关系。
7. “公海 / 体验 / 在服”不应只挂在会员主档上，而应挂在具体服务范围下。
---

## 4. 关键概念
### 4.1 会员主档
会员主档是同一自然人在系统中的统一档案载体。
同一会员只应存在一个主档。手机号是 MVP 阶段识别同一会员的优先依据。
会员主档可挂载多条服务关系，包括：
- 品牌授权关系；
- 门店承接关系；
- 品牌教练服务关系；
- 自由教练服务关系。
### 4.2 服务主体
服务主体是会员授权给谁、谁可以在授权范围内为会员提供服务的核心对象。
MVP 阶段主要支持两类服务主体：
|服务主体|说明|
|-|-|
|品牌|会员授权品牌后，品牌及其下属门店、被分配或邀请的教练可在规则范围内服务该会员|
|自由教练|会员直接授权某个独立教练，品牌和门店不参与该服务关系，MVP 仅预留|

            服务主体
            说明
            品牌
            会员授权品牌后，品牌及其下属门店、被分配或邀请的教练可在规则范围内服务该会员
            自由教练
            会员直接授权某个独立教练，品牌和门店不参与该服务关系，MVP 仅预留
### 4.3 品牌授权关系
品牌授权关系表示会员同意某品牌在授权范围内为其提供训练服务，并访问与服务相关的数据。
管理端邀请和品牌教练邀请，最终都应建立品牌授权关系。
### 4.4 门店承接关系
门店承接关系表示会员进入某一品牌下某个门店的管理范围。
管理端邀请默认建立门店承接关系，并将新会员放入门店公海。
品牌教练邀请也需要关联门店，因为教练隶属于某品牌门店，会员授权后应被该门店管理范围识别。
### 4.5 教练服务关系
教练服务关系表示某个教练可以在授权范围内服务该会员。
教练服务关系分为两类：
|教练类型|关系说明|
|-|-|
|品牌教练|教练基于品牌授权获得服务权限，会员授权的是品牌|
|自由教练|教练基于会员对本人授权获得服务权限，会员授权的是教练本人|

            教练类型
            关系说明
            品牌教练
            教练基于品牌授权获得服务权限，会员授权的是品牌
            自由教练
            教练基于会员对本人授权获得服务权限，会员授权的是教练本人
---
## 5. 管理端邀请规则
### 5.1 适用场景
管理端邀请适用于门店客服、店长、教练主管等管理角色引导会员进入系统，例如：
- 门店前台让到店咨询会员扫码；
- 店长在活动现场邀请用户扫码。
### 5.2 主流程
1. 管理端生成邀请二维码或邀请链接。
2. 邀请码绑定品牌、门店和邀请人。
3. 会员扫码进入会员端。
4. 会员查看品牌授权说明并确认授权。
5. 会员完成手机号登录或注册。
6. 系统识别是否已有会员主档。
7. 系统建立或更新会员与该品牌、该门店的关系。
8. 新会员默认进入该门店公海。
### 5.3 默认规则
|场景|系统处理|
|-|-|
|会员首次进入系统|创建会员主档，授权品牌，进入邀请门店公海|
|会员已有主档，但未授权该品牌|新增品牌授权，进入邀请门店公海|
|会员已授权该品牌，但未进入该门店|建立门店承接关系，进入该门店公海|
|会员已经是该门店公海会员|保持公海身份，不重复创建|
|会员已经是该门店体验会员|保持体验身份，不退回公海|
|会员已经是该门店在服会员|保持在服身份，不退回公海|
|会员在其他品牌或门店已有关系|原关系不受影响，只处理本次邀请对应关系|

### 5.4 核心规则
1. 管理端邀请不自动分配教练。
2. 管理端邀请的新会员默认进入门店公海。
3. 若会员已是该门店会员，系统不得因为再次扫码而改变其原有状态。
4. 管理端邀请不得覆盖其他品牌、门店、教练服务关系。
5. 管理端邀请成功后，管理端可在本门店会员范围内看到该会员。
6. 教练端不展示该会员，除非后续该会员被分配给某位教练，或通过品牌教练邀请建立了教练服务关系。

## 6. 品牌教练邀请规则
### 6.1 适用场景
品牌教练邀请适用于隶属于品牌或门店的教练主动邀请会员进入系统，例如：
- 教练在健身房现场向潜在会员展示邀请码；
- 教练给体验训练会员发送邀请链接；
- 教练让会员扫码授权，以便后续使用 AI 辅助评估、训练计划、训练内容和训练总结。
### 6.2 授权本质
品牌教练邀请不是“会员授权给教练个人”，而是：
> 会员授权给教练所属品牌；该教练基于品牌下的教练身份，成为本次服务承接人。
因此，品牌教练邀请成功后，系统同时建立三层关系：
1. 会员与品牌的授权关系；
2. 会员与门店的承接关系；
3. 会员与邀请教练的体验服务关系。
### 6.3 主流程
1. 品牌教练在教练端生成邀请二维码或邀请链接。
2. 邀请码绑定品牌、门店、邀请教练。
3. 会员扫码进入会员端。
4. 会员查看品牌授权说明，并确认授权该品牌。
5. 会员完成手机号登录或注册。
6. 系统识别是否已有会员主档。
7. 系统建立或更新会员与该品牌、门店的关系。
8. 系统建立或更新会员与邀请教练的体验服务关系。
9. 会员进入邀请教练的体验会员列表。
### 6.4 默认规则
|场景|系统处理|
|-|-|
|会员首次进入系统|创建会员主档，授权品牌，建立门店承接关系，成为邀请教练体验会员|
|会员已有主档，但未授权该品牌|新增品牌授权，建立门店承接关系，成为邀请教练体验会员|
|会员已授权该品牌，但未与该教练建立关系|新增该教练体验服务关系|
|会员已是该教练体验会员|不重复创建，返回当前体验关系|
|会员已是该教练在服会员|保持在服身份，不降级为体验|
|会员已是同门店其他教练体验会员|不影响原体验关系，可新增邀请教练体验关系|
|会员已是同门店其他教练在服会员|不影响原在服关系，可新增邀请教练体验关系|
|会员已是其他品牌教练在服会员|不影响原品牌关系，可新增当前品牌体验关系|
|会员已在该门店公海/在服|新增邀请教练体验关系，若为公海，则状态改为体验；若为在服则不改变状态|

### 6.5 核心规则
1. 品牌教练邀请成功后，会员授权对象是品牌，不是教练个人。
2. 邀请教练自动获得该会员的体验服务权限。
3. 该会员进入邀请教练的体验会员列表。
4. 若会员已是该教练在服会员，不得降级为体验会员。
5. 若会员已是其他教练在服会员，新邀请不得替换原在服教练。
6. 若后续需要将体验会员转为在服会员，应由管理端或具备权限的角色完成正式状态变更。
7. 品牌教练离职、停用或不再属于该品牌门店后，其邀请链接应失效。
8. 品牌教练邀请必须绑定其当前所属品牌和门店，不允许生成无品牌归属的邀请码。

## 7. 自由教练邀请规则预留
### 7.1 功能定位
自由教练邀请用于未来支持不隶属于品牌或门店的独立教练邀请会员进入系统。
MVP 阶段不开放自由教练邀请入口，但底层关系模型需要预留，避免后续重构。
### 7.2 授权本质
自由教练邀请的授权对象是教练本人，而不是品牌。
也就是说：
> 会员授权某个自由教练为自己提供训练服务，该服务关系不属于任何品牌或门店。
### 7.3 未来主流程预留
未来自由教练邀请流程可设计为：
1. 自由教练生成个人邀请二维码或邀请链接。
2. 邀请码绑定自由教练本人。
3. 会员扫码进入会员端。
4. 会员确认授权该自由教练。
5. 会员完成手机号登录或注册。
6. 会员查看自由教练授权说明。
7. 系统识别是否已有会员主档。
8. 系统建立或更新会员与该自由教练的服务关系。
9. 会员成为该自由教练的体验会员。

### 7.5 MVP 阶段处理
MVP 阶段：
1. 不展示自由教练邀请入口。
2. 不开放自由教练注册和邀请能力。
3. 不支持会员直接授权自由教练。
4. 但底层设计中应预留“服务主体类型”差异。
5. 后续扩展自由教练时，不应影响已有品牌授权和品牌教练邀请流程。

## 9. 多关系并存规则
### 9.1 会员主档唯一，服务关系多条
系统应采用以下关系模型：
> 一个会员主档，可以挂载多个品牌授权关系、多个门店承接关系、多个品牌教练服务关系，以及未来多个自由教练服务关系。
不能因为会员已经存在，就拒绝新的品牌、门店或教练邀请；也不能因为新的邀请，覆盖原来的服务关系。
### 9.2 服务关系之间互不覆盖
|已有关系|新动作|处理规则|
|-|-|-|
|A 品牌在服|B 品牌教练邀请|新增 B 品牌授权和 B 教练体验关系，A 品牌在服不变|
|A 品牌 A 教练在服|A 品牌 B 教练邀请|A 教练在服不变，新增 B 教练体验关系|
|A 品牌 A 教练在服|B 品牌 B 教练邀请|新增 B 品牌授权和 B 教练体验关系，A 品牌关系不变|
|门店公海|品牌教练邀请|新增该教练体验关系|
|品牌教练体验|管理端邀请|若已是该门店会员，保持原身份，不退回公海|
|品牌教练在服|管理端邀请|保持在服身份，不降级|

### 9.3 状态不是会员全局唯一状态
会员的公海、体验、在服状态必须带上作用范围。
例如：
- 会员在 A 品牌 A 门店是公海会员；
- 同时在 A 品牌 B 教练下是体验会员；
- 同时在 B 品牌 C 教练下是在服会员；
- 未来也可能同时是某自由教练的体验会员。
因此，页面展示、权限判断、数据统计都不得只按会员主档判断状态。

## 10. 权限与可见范围
### 10.1 管理端权限
管理端只能查看和管理本品牌、本门店授权范围内的会员关系。
管理端可看到：
- 本门店公海会员；
- 本门店体验会员；
- 本门店在服会员；
- 本门店历史服务关系；
- 本门店由管理端或品牌教练邀请进入的会员。
管理端不可看到：
- 会员在其他品牌下的训练数据；
- 会员在其他品牌下的教练关系；
- 未来会员授权给自由教练的服务数据；
- 未授权给本品牌的会员档案内容。
### 10.2 品牌教练权限
品牌教练只能看到与自己存在服务关系的会员。
品牌教练可看到：
- 自己邀请成功的体验会员；
- 分配给自己的在服会员；
- 自己历史服务过的会员；
- 自己服务过程中产生或被授权可见的档案内容。
品牌教练不可看到：
- 同门店公海会员；
- 与自己没有服务关系的会员；
- 其他品牌下的会员训练数据；
- 未来自由教练服务关系下的数据。
### 10.3 自由教练权限预留
自由教练未来只能看到直接授权给自己的会员。
自由教练不可看到：
- 品牌公海会员；
- 品牌管理端数据；
- 会员在其他品牌下的训练数据；
- 会员与其他教练的服务数据。
除非会员后续明确授权共享，否则品牌和自由教练之间的数据默认隔离。
### 10.4 会员端权限
会员端不直接展示“公海、体验、在服”等内部管理状态。
会员端主要展示：
- 已授权品牌；
- 当前服务门店；
- 当前服务教练；
- 未来已授权自由教练；
- 授权管理入口；
- 与本人相关的训练计划、训练内容、评估、总结和档案信息。
会员端应让会员清楚“我授权了谁为我服务”，但不应暴露门店内部销售或管理分组。

## 11. 数据与隐私边界
### 11.1 基础身份匹配
系统可用手机号识别同一会员主档，避免重复建档。
### 11.2 品牌间数据隔离
同一会员授权多个品牌时，不同品牌默认只能访问本品牌服务过程中产生的数据，以及会员授权共享的基础档案信息。
一个品牌不得自动查看另一个品牌下的训练计划、评估结果、训练总结、风险记录和教练备注。
### 11.3 品牌教练与自由教练数据隔离
品牌教练的数据访问来自品牌授权。
自由教练的数据访问来自会员对该教练本人的授权。
二者默认隔离，不得互相查看。
### 11.4 教练间数据边界
同一品牌或门店内，多教练服务同一会员时，可根据业务规则决定是否共享部分训练档案。
MVP 阶段建议：
- 会员基础档案、已确认评估、已确认训练计划、已确认训练总结可按门店服务需要共享；
- 教练个人备注、未确认草稿、当前会话内容默认不共享；
- 他人生成或确认的训练内容，非当前服务教练默认只读；
- 涉及正式档案变更，必须由当前具备权限的教练确认。

## 13. 状态流转规则
### 13.1 管理端邀请
未授权 / 未进入该门店
→ 会员扫码
→ 登录注册
→ 确认授权品牌
→ 进入该门店公海
若已经是该门店会员：
已是该门店公海 / 体验 / 在服
→ 再次扫码
→ 确认授权
→ 原状态保持不变
### 13.2 品牌教练邀请
未与该品牌教练建立服务关系
→ 会员扫码
→ 登录注册
→ 确认授权品牌
→ 建立品牌授权和门店承接关系
→ 成为该品牌教练的体验会员
若已经是该教练会员：
已是该品牌教练体验 / 在服
→ 再次扫码
→ 确认授权
→ 原状态保持不变
若已经是其他教练在服会员：
其他教练在服
→ 扫描新品牌教练邀请码
→ 确认授权品牌
→ 原在服关系保持不变
→ 新增邀请教练体验关系
### 13.3 自由教练邀请预留
未授权该自由教练
→ 会员扫码
→ 登录注册
→ 确认授权自由教练
→ 成为该自由教练体验会员
MVP 阶段该流程不开放。

## 15. 验收标准
1. 管理端邀请新会员后，会员默认进入该门店公海。
2. 管理端邀请已是该门店会员的用户后，该用户原身份不发生变化。
3. 品牌教练邀请新会员后，会员授权的是该教练所属品牌，并默认进入该教练体验会员列表。
4. 品牌教练邀请页不得表达为“授权给教练个人”，必须表达为“授权品牌，由该教练承接体验服务”。
5. 品牌教练邀请已是其他教练在服会员的用户后，原在服关系不受影响，新邀请教练可获得体验服务关系。
6. 同一手机号不会因多次扫码产生多个会员主档。
7. 同一会员可授权多个品牌，且不同品牌数据默认隔离。
8. 同一会员可存在多个品牌教练服务关系，且各关系状态独立。
9. 自由教练邀请能力 MVP 阶段不展示、不开放，但底层关系模型预留服务主体差异。
10. 教练端不展示公海会员，只展示与自己有关的体验、在服、历史会员。
11. 管理端可看到本门店授权范围内的公海、体验、在服会员。
12. 会员端不展示内部公海、体验、在服标签，只展示服务品牌、服务门店、服务教练和授权关系。
13. 邀请码过期、停用、无效时，会员扫码不能建立授权关系。
14. 所有邀请、授权、关系建立、状态保持、重复扫码动作均有留痕。
